Производительность и надёжность¶

Все цифры измерены на Docker-образах из этого репозитория. Стенд: ноутбук AMD Ryzen 5 5500U (6 ядер / 12 потоков), 16 ГБ RAM, Docker Desktop (WSL 2), только CPU. Сырые результаты замера — perf_results.json.

Как измеряли¶

Скрипт backend/tools/benchmark.py использует тот же код, что и работающий бэкенд:

  1. NDTP. 89 096 навигационных пакетов дня 06.01.2026 кодируются в NDTP и разбираются FrameReader + parse_nav потоком по 64 КБ, как их читает приёмник. Ошибок CRC — 0.

  2. Цикл прогноза. Пакеты подаются в TelemetryStore в порядке времени; в 29 моментов T (06:00–20:00 МСК, каждые 30 мин) история ТС за час (в среднем 5 219 точек) уходит на /set_context, точки прогноза (в среднем 6.7 ТС) — на /predict работающего ML-контейнера.

Цикл выполняется в фоне раз в 30 с и не блокирует API и WebSocket (запросы к ML идут в отдельном потоке). Фактическое время последнего цикла на работающей системе — status.elapsed_s в GET /api/predictions (в Docker-стенде 0.57–0.79 с).

Надёжность и деградация¶

Ситуация

Поведение

Проверка

ML-сервис недоступен

API, карта и приём NDTP работают; /api/predictions → state: "error" с текстом ошибки, последние прогнозы остаются с computed_at; после запуска ML цикл сам возвращается в ok (в проверке — через 9 с)

docker compose stop ml / start ml

Обрыв потока NDTP

при закрытии соединения ТС сразу помечаются «нет связи» (при зависшем соединении — через 30 с) и остаются на последней известной позиции; после восстановления источника терминалы переподключаются (в проверке — за 4 с), replayer при обрыве повторяет попытку каждые 5 с

docker compose stop replayer / start replayer

Пакет без GPS-фикса

не затирает последнюю валидную позицию

Мусор или битый CRC в потоке

кадр отбрасывается, приёмник находит следующую сигнатуру 0x7E7E; счётчики bad_crc, skipped_bytes в /api/telemetry/stats

Порт NDTP занят

API стартует, приёмник повторяет попытку каждые 5 с

Падение контейнера

restart: unless-stopped, healthcheck у бэкенда и ML
